## 2. ИМЕНА (нотация C#)
- Корни: Np (numpy) и SciPy (scipy).
- Модули и функции: имя делится на смысловые части, каждая с заглавной буквы:
  ```text
    numpy.linalg.solve          → Np.LinAlg.Solve
    numpy.argmax                → Np.ArgMax
    numpy.cumsum                → Np.CumSum
    numpy.linspace              → Np.LinSpace
    numpy.random.default_rng    → Np.Random.DefaultRng
    scipy.integrate.solve_ivp   → SciPy.Integrate.SolveIvp
    scipy.sparse.linalg.spsolve → SciPy.Sparse.LinAlg.SpSolve
  ```
- Классы: ndarray → NDArray, dtype → DType. Имена, которые уже в PascalCase, не меняются: KDTree, LinearOperator, Generator, PCG64, SVDResult.
- Процедуры BLAS/LAPACK — код процедуры одним словом: dgemm → Dgemm, dgesv → Dgesv (scipy.linalg.lapack.dgesv → SciPy.LinAlg.Lapack.Dgesv).
- Параметры — те же имена в camelCase: axis → axis, keepdims → keepDims. Ключевые слова C# — через @: out → @out.
- Полная таблица соответствий names.csv (имя в Python ↔ имя в C#) строится на этапе 1, я её утверждаю.
  Тест проверяет, что у каждого публичного имени NumPy/SciPy есть ровно одно имя в C#.

## 3. СИГНАТУРЫ И ПОВЕДЕНИЕ 1:1
- Тот же порядок параметров, те же значения по умолчанию. None → null, *args → params.
- array_like (число, список, вложенный список, массив), dtype_like, axis (число | кортеж | None) —
  структуры с неявными преобразованиями (union-типов в C# 14 нет).
- Несколько результатов → кортежи или записи с теми же именами полей, что в оригинале: SVDResult(U, S, Vh).
- Все dtype NumPy, правила приведения типов NEP 50, views и broadcasting — как в NumPy.
- Ошибки — исключения тех же типов и с теми же текстами: LinAlgError, AxisError, ValueError, TypeError, IndexError и т. д.
  Option/Result в API порта не используем.
- Предупреждения (деление на ноль, переполнение и т. п.) — как в NumPy, с аналогом np.errstate.

## 4. ССЫЛКА НА ОРИГИНАЛ В КОММЕНТАРИЯХ — у каждого публичного метода
Пример:
```csharp
    /// <summary>Решает систему a·x = b.</summary>
    /// <remarks>
    /// Оригинал: numpy.linalg.solve — NumPy v2.5.x, numpy/linalg/_linalg.py, строка <N>
    ///   https://github.com/numpy/numpy/blob/v2.5.x/numpy/linalg/_linalg.py#L<N>
    /// Вызывает: LAPACK dgesv — Reference-LAPACK v<версия>, SRC/dgesv.f, строка <N>
    /// </remarks>
    [Original("numpy.linalg.solve", "numpy/linalg/_linalg.py", <N>)]
    public static NDArray Solve(ArrayLike a, ArrayLike b)
```
- Внутри метода у каждого перенесённого фрагмента — однострочный комментарий:
  ```csharp
    // ref: SRC/dgetrf2.f#L<N> — <что здесь делается>
  ```
- Ссылки — только на тег конкретной версии, чтобы номера строк не уплывали.
- Атрибут [Original] нужен порталу (показывает оригинал и ссылку) и тесту: тест проверяет, что ссылка есть
  у каждого публичного метода и указывает на существующий файл и строку в зафиксированных исходниках.

## 5. БЕЗ НАТИВНЫХ БИБЛИОТЕК — ВСЁ НА C#
- NumPy: ядро (ndarray, dtype, ufunc, итератор, приведение типов), своя математика (вместо npymath),
  векторные функции (вместо SVML), сортировки (вместо npysort и x86-simd-sort), FFT (вместо pocketfft),
  random (MT19937, PCG64, Philox, SFC64, распределения), BLAS и LAPACK (вместо OpenBLAS).
- SciPy: QUADPACK, ODEPACK, VODE, DOP853, FITPACK, MINPACK, L-BFGS-B, TNC, SLSQP, HiGHS, DIRECT, ODRPACK,
  SuperLU, ARPACK, PROPACK, Qhull, UNU.RAN, DUCC FFT, спецфункции scipy.special.
- NuGet — только обвязка: xUnit, EF Core + Npgsql, Playwright, Testcontainers, BenchmarkDotNet.

## 6. МНОГОПОТОЧНОСТЬ (паттерн)
- Библиотека — синхронный API, как в NumPy. Тяжёлые ядра (GEMM, блоки LAPACK, операции над большими массивами,
  FFT, квадратуры по сетке точек) внутри режутся на куски и считаются через Task Parallel Library
  (Parallel.For — задачи на пуле потоков). Свои Thread не создаём.
- Общий бюджет потоков (аналог threadpoolctl): параллельные ядра не плодят потоки друг внутри друга.
- Маленькие массивы — в одном потоке; порог переключения подбирается бенчмарком.
- Результат не зависит от числа потоков: разбиение и порядок суммирования фиксированы. Тест сравнивает 1 и N потоков побитово.
- async/await — только для ввода-вывода (БД, сеть, файлы, портал). Синхронный API не оборачиваем в Task.Run «для асинхронности».
- Долгие расчёты с портала — не внутри HTTP-запроса: очередь в Postgres → фоновый воркер (BackgroundService,
  отдельный контейнер) → результат в БД → портал узнаёт через SignalR. Масштаб — несколько воркеров в docker compose.

## 7. ТИПЫ И ПАМЯТЬ В ПОРТЕ
- datetime64/timedelta64 — свои типы: int64 + единица (от лет до аттосекунд), без часовых поясов, правила NumPy
  (месяцы и годы не смешиваются с днями). System.DateTime и NodaTime не используем: у DateTime шаг 100 нс и годы только 1–9999.
- Строки: 'S' — байты, 'U' — UTF-32 (кодовые точки), StringDType — UTF-8 в общем буфере. Сравнение и сортировка — по кодовым точкам.
  string из C# — только на границе API: порядок UTF-16 расходится с NumPy для символов выше U+FFFF.
- longdouble/clongdouble — программный 80-битный float (x87), как у NumPy на Linux x86-64. decimal для этого не годится.
- Форма и шаги массива — встроенный буфер [InlineArray] до 8 измерений, больше — в куче (максимум 64, как в NumPy).
  Срезы и транспонирование не выделяют лишних массивов; счётчики обхода — stackalloc.
- Данные массивов, которые получает пользователь, — обычные массивы .NET (временем жизни views управляет сборщик мусора).
  np.empty — GC.AllocateUninitializedArray (без обнуления), np.zeros — с обнулением.
- ArrayPool — для временных буферов внутри ядер: рабочие массивы LAPACK (work/lwork), упаковка блоков GEMM,
  буферы обхода при приведении типов, FFT, сортировки. Аренда и возврат в try/finally; не полагаться на длину
  и нули арендованного массива. В пул никогда не отдаём память, на которую может ссылаться view.
- Недостающие коллекции (Deque и т. п.) — из библиотеки Std (п. 10); PriorityQueue — из .NET.
- Всё это подтверждается бенчмарками (BenchmarkDotNet): выделения памяти на операцию и время в сравнении с NumPy.

## 10. ДОПОЛНИТЕЛЬНАЯ БИБЛИОТЕКА Std (типы, которых нет в .NET) — для приложения
- Отдельный проект в том же решении, без внешних зависимостей. Её используют портал, API и воркеры.
  Порт (Np/SciPy) может брать из неё только низкоуровневые вещи: UTF-8, коллекции, пул буферов.
  Option/Result и типы времени в API порта не попадают — там 1:1 с NumPy.
- Состав и где используется:
    - `Option<T>`, `Result<T, TError>` — ответы сервисов, проверка данных пользователя, итог задачи в очереди (успех или ошибка с текстом).
    - Время: Instant, LocalDateTime, ZonedDateTime (часовые пояса IANA), Duration, Period —
      история прогонов, сроки задач и кэша, показ времени в часовом поясе пользователя.
    - Utf8String — JSON, CSV и файлы пользователя без перекодирования в UTF-16; сравнение по кодовым точкам.
    - Массивы фиксированного размера по значению ([InlineArray]): `Fixed2/4/8/16<T>`, Bytes32 для хэшей — ключи кэша без выделения памяти.
    - Коллекции: `Deque<T>` (LRU-кэш в памяти, очередь в воркере), `BiDictionary<K,V>` (таблица имён Python ↔ C#),
      `MultiDictionary<K,V>` (индекс документации: модуль → функции), `MultiSet<T>` (статистика запусков функций в портале).
    - BigDecimal и Rational — точный показ чисел в портале (полное десятичное значение double при сравнении с NumPy), точные эталоны в тестах.
    - `Interval<T>` (Contains, Overlaps, Intersect) — фильтры портала (даты, диапазоны значений), допуски в тестах, range-типы PostgreSQL.
    - Пул буферов поверх ArrayPool: аренда с гарантированным возвратом (using), растущий буфер для разбора загрузок (CSV, .npy, JSON).
- Те же правила, что для порта: TDD, на каждый метод минимум 1 позитивный и 1 негативный тест.
  Эталоны тоже из Python: datetime + zoneinfo (время), decimal и fractions (числа), collections.deque (Deque), str.encode('utf-8') (строки).
