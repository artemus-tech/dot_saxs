## Решения

### 1. Репозиторий ✅

- `artemus-tech/dot_saxs`, публичный.
- Работа — ветка и PR на каждый этап. Первый коммит (SPEC.md) сделан прямо в `main`: в пустом репозитории PR не на что открыть.
- Слияние PR (решение пользователя 2026-11-11): PR проверяют двое — ревьюер (отдельный агент Claude, который не писал
  этот код; его итог — комментарием в PR) и пользователь (пишет «согласовано»). Найденное ревьюером исправляется до
  слияния или явно откладывается с записью сюда. После обоих согласований Claude сам переводит PR из черновика и
  сливает его коммитом слияния. Кнопкой «Approve» пользователя не назначить: PR открыт от его же учётной записи, а
  автор не может одобрить свой PR.
- Лицензия — BSD-3-Clause, как у NumPy и SciPy. Лицензии перенесённых компонент (NumPy, SciPy, OpenBLAS, LAPACK и т. д.)
  собираются в `THIRD_PARTY_NOTICES.md` по мере переноса.

  нет в одобренном списке тарифа Pro.
- Поэтому сборка .NET, тесты, эталонный контейнер, Postgres, docker compose и Playwright работают в GitHub Actions

- Вариант на будущее: локальная сессия Claude Code на Mac (там есть .NET и полная сеть) даёт быстрый цикл правка → тест.
  Эталоны и в этом случае — только с x86-64 в CI.

### 3. Версии ✅

NumPy 2.5.4 (не предустановленная в облачной среде 2.5.3), SciPy 1.18.1, .NET SDK 10.0.403 (`global.json`),
Python 3.13, PostgreSQL 17 (решение пользователя от 2026-11-10; до этого было 18). Теги закреплены по коммитам: numpy `a3d0ef1`, scipy `e4e854e`.
OpenBLAS — коммит `446c436e` (источник переноса BLAS и LAPACK, п. 8).
Docker-образы закрепляются по digest, действия GitHub Actions — по SHA коммита. Каждая строка `image:` и `FROM` — с
digest, и у одного образа тег и digest один во всех файлах — это проверяет тест `ImageTests` (ревью PR #2).
- Отложено (ревью PR #2): колёса numpy, scipy и threadpoolctl в эталонном образе ставятся по номеру версии, без

### 4. Эталоны и процессор ✅

Колёса numpy выбирают ядра по процессору, поэтому эталоны — только на x86-64 и только с фиксированными параметрами,
которые записываются в метаданные эталона:
- `NPY_DISABLE_CPU_FEATURES="X86_V4 AVX512_ICL AVX512_SPR"` — остаётся X86_V3 (AVX2 + FMA), это есть почти на любом x86;
  на numpy 2.5.3 проверено: из `X86_V3 X86_V4 AVX512_ICL AVX512_SPR` остаётся `X86_V3`;
- `OPENBLAS_CORETYPE=Haswell`, `OPENBLAS_NUM_THREADS=1` — проверено: OpenBLAS сообщает Haswell и 1 поток.

### 5. Random и своя libm ✅

- Своя libm: `System.Math` даёт разные биты на Linux, Windows и macOS, а распределения random (gamma, beta, binomial,
  poisson…) вызывают exp/log/pow, и расхождение в 1 ULP меняет весь поток.
- exp/log/pow — по ARM optimized-routines (MIT/Apache-2.0), это тот же код, что в glibc.
- sin/cos/acos/atan из glibc (код IBM под LGPL) не переносим. Поэтому vonmises и multivariate_normal (он ещё и
  зависит от LAPACK) сверяются не побитово.

### 6. Известные баги ✅

Исправляем только баги, уже исправленные upstream после наших версий или подтверждённые мейнтейнерами.
Эталон для них — исправленное поведение; каждое отклонение от NumPy/SciPy — в реестре расхождений.

### 7. Негативные тесты ✅

- `TypeError` из разбора аргументов Python (лишний аргумент, не тот тип) в C# ловит компилятор — не воспроизводим.
- Если у функции нет входа, на котором Python бросает исключение (`isscalar`, `iscomplexobj`…),
  вместо негативного теста — граничный случай.

### 8. BLAS и LAPACK: с чем сверяем и откуда переносим (изменено 2026-11-09)

- ✅ Сверка — только с NumPy и SciPy; BLAS-3 и LAPACK — по допуску, как в п. 8 ТЗ.
  Reference-LAPACK (netlib) не используется — ни сборка, ни сверка. Это отменяет в ТЗ эталонную сборку Reference-LAPACK
  (п. 1), сверку с ней (п. 8), а в п. 14 — gfortran и клон Reference-LAPACK.
- Предложение от 2026-11-07 (побитовая сверка с netlib через «эталонный» BLAS без FMA) отменено.
- ✅ Источник переноса BLAS и LAPACK (согласовано 2026-11-09) — исходники OpenBLAS коммита
  `446c436e10450c348169808f1a6b3fae0925c9f7`, из которого собран OpenBLAS в колёсах NumPy 2.5.4. Это код, который NumPy
  реально выполняет: собственные реализации OpenBLAS (например, LU-разложение `getrf`) и встроенная копия LAPACK 3.12.0.
- Ссылки `[Original]` — на этот коммит: `https://github.com/OpenMathLib/OpenBLAS/blob/446c436e…/<файл>#L<N>`.
  Тега у него нет (снимок ветки develop), но ссылка на коммит не уплывает так же, как на тег. Пример из п. 4 ТЗ
  («Вызывает: LAPACK dgesv — Reference-LAPACK…») в порте выглядит как «Вызывает: OpenBLAS gesv — `interface/lapack/gesv.c`».
- Сейчас `[Original]` знает только numpy и scipy (репозиторий — по началу имени Python). Источник (numpy, scipy,
  openblas, cpython — п. 16) атрибут получит вместе с первым переносом из OpenBLAS или CPython (ревью PR #2).
- У SciPy 1.18.1 свой, более старый OpenBLAS (`5ffbf38b`). В порте одна реализация BLAS и LAPACK — по версии NumPy;
  функции линейной алгебры SciPy сверяются с SciPy по допуску, как и все LAPACK-функции.

### 9. Выгрузка эталонов ✅

Компактные кейсы для модульных тестов хранятся в git, бюджет — до 200 МБ. Большие входы генерируются в интеграционных тестах.

### 10. Коллизии имён ✅

C# запрещает члену называться как его класс (CS0542), а часть разных объектов Python после PascalCase склеивается. Правило:
- член совпал с контейнером → `_` в конце: `Np.Fft.Fft_`, `Np.Random.Random_`, `SciPy.Fft.Fft_`, `SciPy.Odr.Odr_`,
  `SciPy.Cluster.Vq.Vq_`, свойство `SciPy.Stats.Covariance.Covariance_`, класс `Np.Polynomial.Polynomial_`;
- модуль совпал с соседним классом → суффикс `Module`: `Np.Polynomial.ChebyshevModule` рядом с классом
  `Np.Polynomial.Chebyshev` (так же Hermite, HermiteE, Laguerre, Legendre, Polynomial);
- объект совпал с классом → `_` у объекта: `SciPy.Stats.Uniform_`, `SciPy.Stats.Logistic_` рядом с новыми классами
  `Uniform`, `Logistic`;
- `scipy.constants` — исходное написание (`g` и `G`).

Остальные случаи (псевдонимы вроде `numpy.ma.round_`) разбираются в `names.csv`.

### 11. Таблица имён names.csv ✅

- Колонка статуса: перенесено / запланировано / псевдоним / исключено + причина. Тест проверяет, что каждое имя Python
  есть в таблице, а каждое «перенесено» существует в сборке с `[Original]`. Так тест проходит и до конца переноса.
- Публичное — модули из `PUBLIC_MODULES` в тестах numpy и scipy плюс обёртки `scipy.linalg.lapack` и `scipy.linalg.blas`
  (их нет в `__all__`, но ТЗ их называет).
- Исключены: `f2py`, `ctypeslib`, `typing`, `lib.mixins`, `LowLevelCallable`, `cython_*`, `scipy.datasets`
  (качает из интернета), `pickle`, протоколы `__array_*__`, `memmap` (данные не в управляемом массиве — противоречит п. 7 ТЗ).
- Спорные разбиения (`nbdtrik`) — одним словом с заглавной, как `Dgemm`: `Nbdtrik`; с пометкой в таблице.
- `scipy.special` делится на слова, как остальное, но строже — только известные слова от трёх букв и `ln`:
  `logsumexp` → `LogSumExp`, `gammaln` → `GammaLn`. Коды Cephes, части с цифрами и части, которые не делятся на
  известные слова, — одним словом: `Ndtri`, `I0e`, `Xlogy` (2026-11-10, раньше части `scipy.special` не делились).
- Буква-обозначение из формулы — заглавная (2026-11-11, решение пользователя): `eval_chebyt` → `EvalChebyT`
  (T — многочлен Чебышёва первого рода), `ellipk` → `EllipK`, `elliprf` → `EllipRF`, `lambertw` → `LambertW`,
  `hyp2f1` → `Hyp2F1`, `hyperu` → `HyperU`; список — в `tools/names/overrides.csv`. Имя остаётся по SciPy, чтобы
  функцию находили по имени из SciPy; понятное описание («многочлен Чебышёва первого рода T_n(x)») — в
  XML-документации, её показывает подсказка редактора. Псевдонимов с понятными именами нет: два имени у одной
  функции — то, от чего мы ушли в п. 21.
- Поля записей — PascalCase: `values` → `Values`; `U`, `S`, `Vh` — как есть.

### 12. Сигнатуры, невозможные 1:1 ✅

- `*args` с keyword-only параметрами после них (`meshgrid`, `einsum`): `params` в C# — только последним, поэтому две
  перегрузки — `params` без опций и массив с опциями в исходном порядке.
- `**kwargs` → `IReadOnlyDictionary<string, object?>`.
- Число результатов зависит от флагов (`unique`, `linspace(retstep)`, `svd(compute_uv)`, `quad(full_output)`) →
  запись со всеми полями: незапрошенные — `null`, есть неявное преобразование в `NDArray`.
- ufunc — статические поля-делегаты, методы им добавляют extension-члены C# 14: работают и `Np.Add(a, b)`,
  и `Np.Add.Reduce(a)`. Остальные вызываемые объекты (`norm(loc=1)`) → `.Invoke(...)`; вызов интерполятора `f(x)` —
  `GetInterpolatedValueAt(x)` и `GetExtrapolatedValueAt(x)` (п. 28).
- `AxisError` в Python наследует и `ValueError`, и `IndexError`. В C# — `AxisError : ValueError` плюс интерфейс-маркер
  для `IndexError`; ловится через `when`.

### 13. Скаляры и NEP 50 ✅

- C# `int`/`long`/`BigInteger` = питоновский int (слабый тип): `np.uint8(1) + 300` → `OverflowError`, как в NumPy.
- `double` = Python float, `Complex` = Python complex.
- `float` и `Half` — сильные float32 и float16.
- `dtype=object` хранит `object?`, арифметика по правилам Python (int → `BigInteger`).

### 14. Ограничения .NET ✅

- Доступа к флагам FPU (MXCSR) нет: предупреждения для `errstate` вычисляются программно, их набор сверяется с NumPy
  тестами. Вывод — в stderr, один раз на место вызова, как в Python.
- Массив .NET — до ~2,1 млрд элементов. Данные хранятся в массиве 16-байтных блоков, это до 32 ГБ на `NDArray`;
  больше — `MemoryError` (в NumPy такого предела нет).

### 15. Детерминизм и скорость

- ✅ Результаты побитово одинаковы на разных машинах (x86 с AVX2 или AVX-512, Mac arm64), а не только при 1 и N потоках.
- ✅ Кроме знака и «начинки» NaN (2026-11-11, решение пользователя): их задаёт процессор. ∞ − ∞ на x86 даёт NaN
  с битами `fff8…`, на arm64 — `7ff8…`; `np.nan` — `7ff8…`, `double.NaN` в .NET — `fff8…`. Поэтому при проверке
  «до бита» любые два NaN равны, всё остальное, включая знак нуля, сравнивается до бита (так NaN сравнивают
  и тесты самого NumPy).
- ⏳ (до этапа 3) Есть ли целевые цифры скорости (например, GEMM не медленнее OpenBLAS в X раз) или бенчмарки только в отчёт?

### 16. Std ✅

- `[Original]` — только там, где поведение 1:1 с CPython (decimal, fractions, deque, datetime), со ссылкой на `Lib/*.py`.
- BigDecimal — минимум: точное значение double, сложение, вычитание, умножение, деление с заданной точностью.
- База часовых поясов IANA — своя встроенная копия фиксированной версии; в эталоне — пакет tzdata той же версии.

### 17. Портал

- ✅ Один ASP.NET-хост (Blazor Server + `/api`) и воркеры в отдельных контейнерах. Воркер сообщает о готовности через
  LISTEN/NOTIFY в Postgres, в браузер — через встроенный в Blazor SignalR, без лишних NuGet.
- ✅ Колбэки (`quad`, `minimize`, `solve_ivp`): код пользователя на сервере не исполняется. Каталог стандартных функций
  плюс свой безопасный парсер выражений: из одного выражения строится и делегат C#, и вызов в эталоне.
- ✅ Playwright: автотест обходит все ссылки и кнопки. В отчёт — по скриншоту на тип страницы и все упавшие,
  полный набор — артефактом.
- ⏳ (до этапа 8) Портал публичный или внутренний (авторизация, лимиты на загрузку и время расчёта)?
  «API» — это REST для внешних клиентов?

### 18. Объём

- ✅ В этап 1 входит сквозной срез на 3–5 функциях (`Np.Add`, `Np.Sum`, `Np.LinAlg.Solve`): эталон → Postgres → тест →

### 22. Строки и столбцы словами ✅ (2026-11-10, уточнено в п. 24 и 30)

| Что | C# | NumPy |
|---|---|---|
| столбец, строка | `GetColumn(2)`, `GetRow(0)` | `a[:, 2]`, `a[0]` |

| по условию | `GetRows().Where(r => r.Max() > 1000)` | `a[a.max(axis=1) > 1000]` |
| суммы и средние | сам через LINQ: `m.GetRows().Select(r => r.Sum())`, `m.GetColumns().Select(c => c.Sum())` | `a.sum(axis=1)`, `a.sum(axis=0)` |

    NumPy прибавляет строку за строкой. До бита — `m.GetRows().ElementWiseSum()`;

### 24. Своя библиотека с NumPy внутри, без `axis` ✅ (решение пользователя 2026-11-10 — 2026-11-11)

- ТЗ меняется: `axis` и `axes` (около 620 функций: numpy — около 240, scipy — около 380) в публичном API нет нигде.
  `[Original]` у наших функций указывает, какой исходник NumPy или SciPy они переносят; сверка — вызовом NumPy
  и SciPy на тех же данных.
- Публичные типы: `Vector` (1-D), `Matrix` (2-D), `CubeMatrix` (3-D), `Tensor4D` … `Tensor8D`, `SparseMatrix`
  (разреженная, п. 25), `ColumnDictionary` (таблица с именами столбцов, п. 30) и обычные числа.
  Наследования нет: каждый тип хранит внутри массив-двигатель без копирования и выставляет только
  то, что имеет смысл для своей размерности, — `matrix.Diff()` не компилируется. NumPy пробовал наследование
  (`np.matrix`) и теперь не рекомендует его.
- Внутри — ядро до 8 измерений (уточнено 2026-11-11; в NumPy предел 64): память, тип чисел, view без копирования,
  поэлементная арифметика, суммы в том же порядке, что у NumPy. Без broadcasting и без функций NumPy с `axis`.
  Все публичные типы — тонкие обёртки над ним; пользователь ядро не видит, номера измерений наружу не выходят
  (исключение — перестановка размеров, п. 29).
  Больше 8 измерений — ошибка; предел — одна константа.
- `Tensor4D` … `Tensor8D` генерируются из одного шаблона. Каждый делится по первому размеру на тип на ступень ниже:
  `t4.GetCubeMatrixByIndex(i)` → `CubeMatrix`, `t5.GetTensor4DByIndex(i)` → `Tensor4D` и т. д.; коллекции для LINQ
  (`GetCubeMatrices()`…), поэлементная арифметика, функции от всего массива (`Sum`, `Mean`, `Max`), `Flatten()` →
  `Vector`, загрузка `LoadTensor4D` … `LoadTensor8D`. Функции вдоль направления — только у `Vector`, как везде.
- Функции «вдоль линии» (`diff`, `sort`, `cumsum`, `trapezoid`, БПФ, фильтры, статистика, интерполяция) переносятся
  в одномерном виде — только для `Vector`, без `axis`: пользователь сам передаёт нужные `x` и `y`. Перенос не
  дословный, строки с `axis` выкидываются; сверка — вызовом NumPy и SciPy на тех же векторах, побитово.
- Таблицы и кубы — перебором через LINQ: `GetRows()`, `GetColumns()`, `GetMatrices()`. `Select` — для
  каждого элемента; поперёк элементов коллекции — `ElementWiseSum()` (`matrix.GetRows().ElementWiseSum()` побитово
  равно `np.sum(a, axis=0)`), так же будут `ElementWiseMean()` и `ElementWiseMax()` (2026-11-12). `.ToVector()`, `.ToMatrix()`, `.ToCubeMatrix()` собирают результат обратно; столбцы
  возвращаются столбцами. Частые операции — готовыми методами с направлением в имени (п. 22), кроме сумм и средних:
  их человек считает сам через LINQ (2026-11-12).
- Двумерные по сути алгоритмы — сразу на `Matrix` и `CubeMatrix`, тоже без `axis`: `a.Solve(b)`,
  `image.GaussianFilter(2)`, `image.Fft2()`.
- Форма меняется словами. `Matrix`: `AppendRow`, `AppendColumn`, `PrependRow`, `PrependColumn`, `InsertRow`,
  `InsertColumn`, `RemoveRow`, `RemoveColumn`, `Matrix.FromRows(…)`, `Matrix.FromColumns(…)`. `CubeMatrix`:
  `GetMatrixByIndex(k)` (например, кадр), `GetMatrices()`, `AppendMatrix(…)`, `InsertMatrix(…)`, `RemoveMatrix(…)`;
  значения одной точки во всех матрицах — `cube.GetMatrices().Select(m => m[row, column]).ToVector()`.
  Слова `Layer` и `Tube` не используем.
  Методы возвращают новый объект, как `Append` в LINQ и `np.append`; размеры проверяются, ошибка называет, что с чем
  не сошлось.
- Загрузка: `LoadVector`, `LoadMatrix`, `LoadCubeMatrix`, … `LoadTensor8D` — когда тип известен заранее; ошибка,
  если в файле другая размерность. `Np.Load(path)` — когда не известен: возвращает тип по файлу (`Vector` …
  `Tensor8D`, `ColumnDictionary` — если в файле есть имена столбцов, п. 30), дальше `switch` по типу; для этого
  у всех типов общий интерфейс (имя — на этапе 2). `Np.GetFileShape(path)` — размеры из заголовка, без чтения данных.
  Номер матрицы
  куба: если у размеров в файле есть подписи (HDF5) — по подписи, а если по ним не понять — ошибка со списком
  подписей; если подписей нет (.npy) — первый размер, без угадывания. Другой порядок пользователь переставляет сам:
  `cube.SetIndexOfMatrix(2)` (п. 29).
- Позиция максимума и минимума: у `Vector` — `ArgMax()`, `ArgMin()`, как в NumPy; у `Matrix` своей нет —
  `matrix.Flatten().ArgMax()` или LINQ.
- Ковариация и корреляция — как в NumPy, результат совпадает с `np.cov` и `np.corrcoef`: `Cov(m)` — величины
  в строках, как в NumPy; `Cov(x, y)` для двух векторов — матрица 2×2, как `np.cov(x, y)`. Параметра `rowvar`
  нет: величины в столбцах — `Cov(m.Transpose())`, как `np.cov(m.T)`. `CorrCoef` — так же.
- У `Matrix` нет `Flip()`: в NumPy без `axis` он переворачивает сразу в обе стороны. Вверх ногами —
  `GetRows().Reverse()`, каждую строку задом наперёд — `GetRows().Select(r => r.Reverse())`.
- `PolyFit` и `CurveFit` — только для `Vector`, несколько кривых — перебором. В NumPy `polyfit` с двумерным `y`
  подгоняет столбцы, а `curve_fit` ждёт несколько переменных строками.
- Операторов `+ − * /` у массивов нет (2026-11-11). Поэлементные вычисления — `Select` с индексами, это тот же цикл
  `for`: `a.Select((x, i, j, k) => (x - b[i, j, k]) / c[i, j, k] * 2.5)`; «вычесть вектор из каждой строки» —
  `m.Select((x, row, column) => x - v[column])`. Размеры других массивов в формуле не сверяются: меньше — ошибка
  выхода за границы, больше — молча возьмётся часть. Матричное произведение — `LinAlgMultiply`.
- Параллельность — явно, как в PLINQ: `a.AsParallel().Select(…)`; результат поэлементных вычислений от этого
  не меняется. Суммы считаются параллельно только так, чтобы биты совпали с NumPy (он складывает половинками).
  Async — только для чтения и записи файлов: `await Np.LoadCubeMatrixAsync(path)`.
- Принцип минимального API (2026-11-11) — для поэлементных вычислений: их не делаем методами, а пишем через LINQ.
  Работа с формой (строки, столбцы, диапазоны, Append/Insert/Remove — п. 22) остаётся в основных типах, и её
  должно быть много. В `DotSaxs.Extensions` — редкие сокращения вроде `cube.GetValuesByPosition(row, column)`.
  - Поэлементные функции — 106 ufunc NumPy и 232 функции `scipy.special` — только для чисел: `Np.Exp(x)`,
    `Special.Gamma(x)`; к массиву — `v.Select(Np.Exp)`. Сами функции — перенос кода NumPy и SciPy, а не `Math.Exp`,
    иначе последние биты разойдутся с NumPy.
  - Свои `Sum`, `Mean`, `Std`, `Sort` и подобные есть у всех типов: у стандартного LINQ результат другой
    (сумма десяти 0.1: подряд — 0.9999999999999999, у NumPy — 1.0; NaN при сортировке у LINQ первым, у NumPy
    последним). C# сам выбирает метод типа, а не LINQ, поэтому `v.Sum()` даёт ровно результат NumPy.
  - Функции вдоль линии (`Diff`, БПФ, фильтры) и линейная алгебра — тоже методы: через LINQ они не пишутся.
- Вид чисел — в типе (решение пользователя 2026-11-11): `Vector<double>`, `Vector<int>`, `Vector<bool>`,
  `Vector<Complex>`, так же `Matrix<T>`, `CubeMatrix<T>`, `Tensor4D<T>` … `Tensor8D<T>`, `SparseMatrix<T>`,
  `ColumnDictionary<T>`. Смешивать виды чисел — только явно (`counts.ToDouble()`); функции, которые в NumPy из целых дают дробные (`Sqrt`, `Mean`),
  возвращают дробные, как NumPy. Имя пересекается с `System.Numerics.Vector<T>`: в файле с `using System.Numerics`
  писать полное имя или псевдоним через `using`. В примерах этого файла `<double>` для краткости опущен.
- Форматы файлов. Свои форматы NumPy (.npy, .npz, текст — `np.load`, `np.loadtxt`) — в основной сборке, это функции
  NumPy. Остальные (HDF5 и т. п.) — отдельная сборка на формат: она только создаёт наши типы, вычисления о файлах

### 28. Вызов интерполятора ✅ (2026-11-11)

- В Python интерполятор вызывают как функцию: `cs(1.5)`. В C# объект скобками не вызывается, поэтому у всех
  интерполяторов `scipy.interpolate` (`CubicSpline`, `PPoly`, `BSpline`, `RegularGridInterpolator`…) два метода:
  - `GetInterpolatedValueAt(x)` — значение кривой в точке; за краем точек — NaN, как `cs(x, extrapolate=False)`;
  - `GetExtrapolatedValueAt(x)` — продолжает кривую за край, как `cs(x)` в SciPy по умолчанию.
- Внутри точек оба метода дают одно и то же: `GetInterpolatedValueAt(1.5)` и `GetExtrapolatedValueAt(1.5)` у сплайна
  по точкам x³ — 3.375000000000001. За краем: `GetInterpolatedValueAt(4)` — NaN, `GetExtrapolatedValueAt(4)` —
  64.00000000000003. При переносе кода с Python `cs(x)` → `GetExtrapolatedValueAt(x)`.
- Многомерные — так же: `grid.GetInterpolatedValueAt(x, y)`. Что значит «за краем» у каждого класса, уточняем на
  этапе 6: у `RegularGridInterpolator` SciPy по умолчанию бросает ошибку, у `LinearNDInterpolator` за выпуклой
  оболочкой точек даёт NaN, у `RBFInterpolator` края нет.
- Имена предложил пользователь: в стиле `GetRow` и `GetColumn` (п. 22). В `names.csv` — строки `….__call__`.

### 29. Перестановка размеров ✅ (решение пользователя 2026-11-11)

- Каждый тип делится по первому размеру на части — типы на ступень ниже (п. 24): куб — на матрицы, `Tensor4D` — на
  кубы. Метод, который выбирает, какой размер станет номером части, называет тип части: `cube.SetIndexOfMatrix(n)`,
  `t4.SetIndexOfCubeMatrix(n)`, `t5.SetIndexOfTensor4D(n)` … `t8.SetIndexOfTensor7D(n)`. У `Matrix` это `Transpose()`.
- `n` — номер размера с нуля в нынешнем порядке (сразу после чтения — как в файле, `Np.GetFileShape(path)`). Размер `n`
  становится первым, остальные идут в прежнем порядке — как `np.moveaxis(a, n, 0)`. Пример: в файле куб
  512 × 512 × 30, где 30 — номер кадра; `cube.SetIndexOfMatrix(2)` даёт куб 30 × 512 × 512 — 30 матриц 512 × 512.
- Результат — новый объект над теми же данными, без копирования, как у `np.moveaxis`.
- Это исключение из правила «номера измерений наружу не выходят» (п. 24): у размеров в .npy подписей нет, назвать
  нужный можно только номером. `np.rollaxis(a, n)` — то же самое; переноса не на первое место и `np.swapaxes` нет.
- Имена методов предложил пользователь.

### 30. Имена столбцов — `ColumnDictionary` ✅ (решение пользователя 2026-11-11, меняет п. 22)

- Имена столбцов бывают в .npy — у структурированного массива (в заголовке `'descr': [('q', '<f8'), ('I', '<f8')]`,
  в NumPy столбец берут как `a["q"]`) — и в тексте — в строке заголовка (`np.genfromtxt(path, names=True)`).
- `Matrix` хранит только числа. Таблица с именами — свой тип `ColumnDictionary<T>`: словарь «имя → столбец
  (`Vector<T>`)» в порядке файла. Наследования нет, но его можно передать туда, где ждут словарь только для чтения
  (`IReadOnlyDictionary<string, Vector<T>>`).
- Отвергнуто: имена полем в `Matrix` — около 15 методов формы следили бы за именами, а `m.GetRows().Where(…).ToMatrix()`
  их терял бы; обычный словарь .NET — в него можно положить столбец не той длины; наследование от словаря — его методы
  не переопределить, проверку длины не вставить.
- Методы: `data["q"]`, `data.GetColumnByName("q")` и `data.GetColumnsByNames("q", "I")` (переехали из `Matrix`, п. 22),
  `data.GetColumn(1)` — по номеру, `data.Names`, `RowCount`, `ColumnCount`. `data.GetRows()` — строки, их числа тоже
  по имени: `data.GetRows().Where(r => r["q"] <= 0.02).ToColumnDictionary()` отбирает точки сразу во всех столбцах.
  `data.ToMatrix()` — только числа; `m.ToColumnDictionary("q", "I")` — дать имена столбцам матрицы. Все столбцы
  всегда одной длины. Методы возвращают новый объект (п. 24).
- Чтение. `Np.LoadColumnDictionary(path)` — файл с именами; если имён нет — ошибка. `Np.Load(path)` отдаёт
  `ColumnDictionary`, если в файле есть имена (п. 24). Любой `Load…` для файла с именами даёт только числа, имена
  отбрасывает; имена из заголовка, без чтения чисел, — `Np.GetFileColumnNames(path)`. В тексте заголовок не угадываем:
  `Np.LoadColumnDictionary("saxs.dat")` считает первую строку именами, `Np.LoadMatrix("saxs.dat")` читает только числа.
- Серия таблиц (структурированный массив с двумя размерами, например 100 кадров по 3 точки) — через куб:
  `Np.LoadCubeMatrix(path).GetMatrices().Select(m => m.ToColumnDictionary(names)).ToArray()`. С тремя размерами
  и больше — ошибка. Чаще серии хранят в .npz: `q` — вектор, `I` — матрица (`Np.LoadZ`).
- Один вид чисел на все столбцы: целый столбец при чтении в `ColumnDictionary<double>` становится double. Кубов
  и тензоров с именами нет. Публичных типов становится 10.
- Сборка — основная `DotSaxs`, рядом с `Matrix` (п. 26). В Std, где `Deque`, — нельзя: Std не знает о `Vector`, а две
  сборки не могут ссылаться друг на друга.
- Функции `numpy.rec` и `numpy.lib.recfunctions` раскладываются по методам `ColumnDictionary` на этапе 2; уже
  разложены `structured_to_unstructured` → `data.ToMatrix()` и `unstructured_to_structured` → `m.ToColumnDictionary(…)`.

### 31. Маскированные и строковые массивы не переносим ✅ (решение пользователя 2026-11-11)

- `numpy.ma` (маскированные массивы: плохие точки скрыты маской) и `numpy.strings`, `numpy.char` (массивы строк)
  не переносятся: пользователь делает это сам через LINQ. Без плохих точек — `v.Where(x => double.IsFinite(x)).ToVector()`,
  по своей маске — `v.Where((x, i) => good[i]).ToVector()`; строки — `string` и LINQ.
- Мусор во входных данных — исключение (`ValueError`) с местом, где он найден, а не маска и не NaN: не число в текстовом
  файле, пустое поле, строка с другим числом столбцов. Так делает `np.loadtxt` (`could not convert string 'abc' to
  float64 at row 1, column 2.`); `np.genfromtxt` на месте не числа и пустого поля ставит NaN — у нас тоже исключение.
  `nan` и `inf`, записанные в файле, — числа, а не мусор.

### 32. Исключения и предупреждения ✅ (решение пользователя 2026-11-11, меняет п. 3 ТЗ)

- Библиотека (`DotSaxs`, сборки SciPy) только бросает исключения: сама их не ловит и в лог не пишет, логгера у неё
  нет. Ловит только там, где сам NumPy или SciPy ловит ошибку в своём коде на Python, — это переносится как есть.
- Перенесённые функции — тот же тип и тот же текст, что у NumPy и SciPy (п. 3 ТЗ); тест сверяет с эталоном:
  `Solve` с вырожденной матрицей — `LinAlgError` с текстом `Singular matrix`. Наши методы без оригинала
  (`AppendColumn`, `GetColumnByName`…) — тип как у похожей функции NumPy (`ValueError`, `IndexError`), текст свой,
  словами нашего API: «столбец из 5 чисел, а в матрице 3 строки».
- Свои тексты — в одном файле `src/DotSaxs/Messages.json` (решение пользователя 2026-11-11): у каждого текста оба
  языка рядом, `en` и `ru`, чтобы переводы не расходились. Язык — из конфига (п. 33), по умолчанию английский. Тексты
  перенесённых функций не переводятся: они всегда английские, слово в слово как в NumPy. Тест проверяет, что у
  каждого текста есть оба языка и одинаковые места для чисел.
- Деление на ноль, переполнение, недопустимое значение в наших функциях (`Np.Log(0)`, `Np.Exp(1000)`,
  `Np.ArcCos(2)`, `Sum`) — по умолчанию исключение `FloatingPointError` с текстом NumPy
  (`divide by zero encountered in log`), как `np.seterr(all="raise")`; в NumPy по умолчанию — только предупреждение.
  Числа, которые округляются до нуля (underflow), — не ошибка, как в NumPy. Кому нужны `inf` и `nan` — на всю
  программу через конфиг (п. 33), на кусок кода — `using (Np.ErrState(divide: "ignore")) { … }`. `ErrState` нужен
  и внутри: NumPy и SciPy сами оборачивают расчёты в `errstate`, этот код переносится как есть. `Np.SetErr` не
  делаем — вместо него конфиг. Как и в NumPy, ошибка проверяется после расчёта всего массива; текст — первого
  случая в порядке «деление, переполнение, недопустимое значение». Что делать в режиме `warn` без Python —
  решаю при переносе остального `errstate`.
- Переполнение целых (решение пользователя 2026-11-12) — тоже исключение `FloatingPointError` (`overflow encountered
  in add`), как у NumPy с `over="raise"` для одиночного числа. Массивы NumPy молча считают по кругу (`uint8` 200 + 100
  = 44): число неверное, и никто об этом не знает. Повторить NumPy — явно: `Np.ErrState(over: "ignore")`.
- Обычная арифметика C# в лямбдах (`v.Select((x, i) => x / w[i])`) и функции .NET (`Math.Sqrt(-1)` — так по
  `names.csv` переносится `np.sqrt`) исключений не бросают: `inf` и `nan` — молча, перехватить их библиотека не может.
  В NumPy `np.sqrt(-1.0)` тоже не уходит в комплексные числа: `nan` и предупреждение; комплексный ответ — у
  комплексного входа (`np.sqrt(-1+0j)` → `1j`) или у `np.emath.sqrt(-1)` (у нас `Np.EMath.Sqrt`, этап 5).
- Тесты сверяют оба режима: с `ignore` — числа до бита, по умолчанию — исключение с текстом первого предупреждения,
  записанного в эталоне.
- Приложение (этап 8). `DotSaxs.Data` ловит только то, что умеет исправить (обрыв соединения с базой — повтор
  запроса). Воркер ловит исключение вокруг одной задачи и не падает: одна запись в лог (тип, текст, стек, номер
  задачи, функция) и итог задачи в базе — `Result` с текстом ошибки (п. 10 ТЗ). API: ошибка в данных пользователя
  (`ValueError`) — ответ 400 с текстом, остальное — 500 и запись в лог.
- В лог пишем один раз и только наверху, через `ILogger` .NET; «записать в лог и бросить дальше» внизу не делаем.

### 33. Конфиг библиотеки ✅ (решение пользователя 2026-11-11)

- Один конфиг на всю библиотеку — штатный файл .NET `<программа>.runtimeconfig.json`, раздел `configProperties`.
  Библиотека читает его через `AppContext`, без зависимостей. В проекте программы ключ задают так:
  `<RuntimeHostConfigurationOption Include="DotSaxs.Language" Value="ru" />` (или в `runtimeconfig.template.json`),
  в готовой программе — правят файл рядом с ней.

| Ключ | Значения | По умолчанию | Зачем |
|---|---|---|---|
| `DotSaxs.Language` | `en`, `ru` | `en` | язык своих текстов исключений (п. 32) |
| `DotSaxs.ErrState.Divide`, `.Over`, `.Under`, `.Invalid` | `raise`, `ignore` | `raise`, `raise`, `ignore`, `raise` | ошибки чисел: исключение или молча `inf` и `nan` (п. 32) |
| `DotSaxs.Threads` | число | все ядра | сколько потоков берут тяжёлые расчёты (этап 3); на результат не влияет, только на скорость |

- Что сильнее чего: блок `Np.ErrState` > конфиг > значения по умолчанию.
- В конфиг не кладём: то, что меняет результат вычислений (он обязан совпадать с NumPy до бита на любой машине);
  строку подключения к базе, кэш и очередь — это настройки портала и воркеров в их `appsettings.json`; зерно
  случайных чисел — его передают генератору; лог — библиотека в лог не пишет. Позже может добавиться
  `DotSaxs.Print.Precision` — для вывода массивов текстом, как `np.set_printoptions`.
